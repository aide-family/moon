# 品牌色双模式视觉验收审计 — Alioth Web

**审计对象**：`web/src/index.css` 主题 token + `web/src/components/ui/*` 与业务组件实际用色
**审计日期**：2026-10-28
**方法**：WCAG 2.1 相对亮度公式实算（脚本见 `tmp/contrast-audit.py`、`tmp/gen_tables.py`），非目测
**判定阈值**：正文 AA 4.5:1 / 大字 AA 3:1 / AAA 7:1 / 非文本组件与焦点指示 3:1（WCAG 1.4.11、2.4.11）

---

## 决策：HOLD

两个原因，任一单独成立都足以阻断：

1. **给定的 7 个品牌色在本仓库中一个都不存在。** 仓库实际品牌主色是 `--primary: #1677ff`。这 7 个色是「候选/待引入」色板，不是「现有用色」。任务里「按实际用色审计」的前提与仓库事实不符，必须先澄清再谈验收。
2. **无论按现状色还是按 7 个候选色，两套方案都存在硬性 AA 不达标**，且不达标位置集中在最高频元素上：单色（primary）chip、主按钮、焦点环、侧边栏选中态。焦点环 `ring-ring/50` 在现状 `#1677ff` 下仅 **1.95:1**（浅）/ **2.02:1**（深），远低于 3:1 —— 这是当前已发布代码就存在的缺陷，与换不换品牌色无关。

## 0. 审计前提修正（必须先解决）

| 项 | 任务假定 | 仓库实际 |
|---|---|---|
| 品牌主色 | 7 个色任选/共存 | 单一 `#1677ff`，浅深两模式**完全相同** |
| 品牌色定义位置 | 应在 token 中集中 | 硬编码 `#1677ff`：`index.css` **15 处**、`lib/chart-colors.ts` 1 处；另有 **14 个空状态插图 SVG 内共 181 处** `fill="#1677ff"` |
| 可切换品牌色 | 隐含存在主题切换 | `theme-provider.tsx` 只切 `light/dark`，**没有任何品牌色切换能力** |

**这意味着**：引入 7 个品牌色不是「调色」，而是要先做 token 重构。当前状态下改 `--primary`，页面顶部 `--app-gradient` 仍是硬编码的蓝色 `rgba(22, 119, 255, 0.08)`（`index.css:100`、`:148`），会立刻出现「按钮变橙、顶部光晕还是蓝」的品牌错位。`--accent-foreground`、`--ring`、`--chart-1`、`--sidebar-primary`、`--sidebar-accent-foreground`、`--sidebar-ring` 同样各自硬编码，共 6 个次要 token 需要跟着品牌色联动。

**最被低估的一处是 14 个空状态插图。** `assets/undraw/*.svg` 是错误页（403/404/502/503）、通知、服务健康、SSH、权限等页面的空状态与错误态配图，全部把品牌色写死成蓝色 `#1677ff`，单个文件最多 60 处（`service-health.svg`）。换任一品牌色后，这些插图会与界面主色直接冲突，且无法用 CSS 变量修复——必须替换为 `fill="currentColor"` 或重新导出。这是一笔被漏算的改造量。

> 结论：**在任何一色验收之前，必须先完成「品牌色单源化」**。否则 7 色验收结论无法落地。

## 1. 产品透镜

Alioth 是面向运维/SRE 的多租户可观测与告警平台。用户每天在这里完成的是：盯实时告警、判断哪条需要响应、配置规则与通知通道。界面密度高、表格为主、状态色语义强（`status-badge.tsx` 集中定义了 success/warning/danger/info/violet/primary 七档）。

因此品牌色的角色被严格限制：**它只承担"可交互/可点击/当前选中"的指示职能**，不承担状态语义（状态已被红黄绿蓝紫占用），也不应成为大面积装饰。这个定位决定了后续所有裁决——品牌色必须首先是一个**可靠的交互指示色**，其次才是视觉识别色。

这也是判断「深色模式过饱和」的基准：一个每天被注视 8 小时的运维控制台，主色是**背景噪音**，不是主角。

| warning `#b45309` | 4.47 ⚠（差 0.03） | `#fcd34d` 11.35 ✅ |

**这是全篇最有力的证据**：同一个文件、同一个 `toneClasses` 映射表，5 个语义色都做了双模式取值，唯独 `primary` 直接写 `bg-primary/10 text-primary`，两个模式共用同一个值，两个模式都不达标。primary 是这套色彩系统里唯一没有遵守自身规则的成员。

修正方式因此不是发明新方案，而是**让 primary 加入它已经在用的规则**。

### 3.1 读表要点

**没有一个色在两个模式下都合格。** 这是最关键的结论。7 色中：

- **`#722169` 皇家紫是唯一在浅色模式全部达标（9.39）的色**，但在深色底 `#0b1120` 上只有 **1.92:1**，是全表最差的一个。紫在深底上等于隐形。

- **`#41B5C2` 碧青、`#EB6D98` 梅洛粉、`#DB7A0E` 暖阳橙** 三者浅色模式全在 2.3–3.0 区间，属于「看得到轮廓、读不清字」的地带，比彻底不可见更危险。
- **`#5E8034` 翠微** 是唯一在两个模式都落在 4.1–4.6 边缘的色，两边都是「差一点」，两边都不可靠。
- **`#5A92E5` 矢车菊蓝** 浅色 3.01（仅大字号边缘）、深色 5.99（AA），是 7 色中双模式差异最小的，但仍不满足浅色正文。

`#0F1115` 与 `#1A1D23` 两个深底实测差异不大（同一色在两者间差 0.4–0.9），但 `#1A1D23` 始终更宽松——因为更亮。若深色底真要用 `#1A1D23`，所有色的深色比率会比仓库现值 `#0b1120` 略降，验收标准需按实际底色重算，不能混用。

## 4. 高明度色在浅色模式的风险与修正（要求 3）

### 4.1 已证实的风险

`bg-primary/10 + text-primary` 是全仓库最高频的品牌色应用模式，至少出现在 10 个组件：`status-badge.tsx`、`filter-toggle.tsx`（`text-xs`）、`app-shell.tsx` 头像块、`tenant-switcher.tsx`（`text-xs`）、`overview/cards.tsx`、`cluster/detail/overview-cards.tsx`、`message/index.tsx`（`text-[10px]`）、`namespace/index.tsx`、`workers/index.tsx`。

实测（表 3）：**浅色模式下 6/7 候选色不达标**，其中柠檬黄 **1.42:1**、碧青 2.15、梅洛粉 2.54、暖阳橙 2.66、矢车菊蓝 2.74 五色属于"完全读不清"。且这些 chip 多为 10–12px 小字，比正文更严格。

**柠檬黄是极端案例**：作为 10% tint 的文字，1.42:1 已低于"任何视觉可辨"的下限。它在浅色模式不能作为文字色使用，无论字号多大。

### 4.2 修正方案（三条，按优先级）

**① chip 文字改用「以 tint 为实测底」压深后的专用 token。** 不能简单压深到对白底达 4.5（那样压得不够，实测仅 4.0–4.4，仍失败——这是本次审计中一个容易踩的坑）。必须以实际 tint 背景为基准压深：

| 品牌色 | 10% tint 底 | chip 专用文字 | 实测 |
|---|---|---|---|
| 暖阳橙 | `#F5EDE4` | `#A25A0A` | 4.53 ✅ |
| 矢车菊蓝 | `#E8F0FA` | `#436CA9` | 4.62 ✅ |
| 翠微 | `#E9EEE8` | `#56742F` | 4.54 ✅ |
| 碧青 | `#E6F3F6` | `#2B7780` | 4.57 ✅ |
| 柠檬黄 | `#F8F5E7` | `#876D19` | 4.54 ✅ |
| 梅洛粉 | `#F7ECF2` | `#A94E6D` | 4.56 ✅ |
| 皇家紫 | `#EBE4ED` | `#722169` | 7.89 ✅ |

**② 高明度色取消"tint + 同色文字"结构。** 柠檬黄、碧青这类色（相对亮度 Y > 0.35）在浅色模式应改为：**中性底 + 彩色圆点/图标 + 深色文字**。文字读的是中性前景（AAA），品牌色只承担 8–10px 的识别点。这是运维控制台里更合适的做法，也避免小字承载品牌色。

**③ chip 底色加深、文字放开。** `bg-primary/10` → `/14`~`/16` 可以把深色模式下的层级拉开，但对浅色模式改善有限，属次要手段。

### 4.3 附带的非文本失效

表 5 显示，高明度色在浅色模式的**非文本**用途同样失效：

- **进度条 `bg-primary/70`**：6/7 候选色对轨道 `#f1f5f9` < 3:1（柠檬黄 1.27、碧青 1.71；仅皇家紫 4.21 通过）。现状 `#1677ff` 也只有 2.59，**同样是已存在缺陷**。修正：进度条填充改用品牌色的压深值（表 4 第 3 列），不要用透明度。
- **日历选中 `bg-primary/15`**：7/7 对白色 popover 均 < 1.6:1。作为"选中区间"的视觉承载完全不够。修正：区间底色用 `/15` 保留，但**必须叠加 1px 品牌色描边或左侧色条**承担 3:1 指示。
- **hover `bg-primary/80` 白字**：7/7 候选色在 hover 时对比度**全部下降**（暖阳橙 3.09 → 2.47，皇家紫 9.83 → 5.98，降幅最大 -3.84）。用不透明度做 hover 在亮色品牌上必然恶化。修正：hover 改为"压深 8–12% 的同色相"，而非"向背景混合"。

## 5. 深色模式的过饱和、发光与疲劳（要求 4）

### 5.1 问题一：主色在深色模式未做任何调整

`--primary` 在 `.dark` 中与浅色模式**完全相同**（`#1677ff`，饱和度 S=100%）。而同一个 `index.css` 的 `.oauth-brand` 却明确定义了深色提亮规则：

```css
.oauth-brand[data-provider="GITEE"]    { --oauth-brand: #c71d23; }
.dark .oauth-brand[data-provider="GITEE"] { --oauth-brand: #ff7875; }  /* 提亮 */
.dark .oauth-brand[data-provider="FEISHU"] { --oauth-brand: #7aa2ff; }  /* 提亮 */
.dark .oauth-brand[data-provider="DINGTALK"] { --oauth-brand: #69b1ff; } /* 提亮 */
```

于是产生了直接的内部矛盾：**钉钉登录按钮的主色在深色模式是 `#69b1ff`，而应用自己的主色仍是 `#1677ff`。** 同一个深色页面上，第三方品牌色比自家品牌色更亮、更柔和。文件里的注释甚至写着「深色模式需要提亮，官方浅色值在深色卡片上分辨不出来」——规则写对了，主色自己没遵守。

### 5.2 问题二：高饱和 100% 的主色大面积使用

`#1677ff` 的 HSL 饱和度为 **100%**。在 `#0b1120` 这种低亮度底色上，一个 100% 饱和的蓝色实心块是整屏色度最高的元素。候选色中同样高危的：

| 品牌色 | 饱和度 | 相对亮度 Y | 深色模式风险 |
|---|---|---|---|
| 柠檬黄 `#FACA2E` | 95.3% | **0.628** | **高**：12.15:1 的实心大按钮在暗背景上产生眩光，长时间注视疲劳 |
| 碧青 `#41B5C2` | 51.4% | 0.381 | 中高：7.72:1，实心使用偏亮 |
| 梅洛粉 `#EB6D98` | 75.9% | 0.309 | 中 |
| 暖阳橙 `#DB7A0E` | 88.0% | 0.290 | 中 |
| 矢车菊蓝 `#5A92E5` | 72.8% | 0.284 | 中 |
| 皇家紫 `#722169` | 55.1% | 0.057 | **反向问题**：1.92:1，深色模式不可见 |

**高对比不等于好体验。** 12:1 的柠檬黄实心区域在暗环境中属于眩光，WCAG 只规定下限不规定上限，但运维控制台的连续使用场景需要上限。建议：**相对亮度 Y ≥ 0.45 的品牌色在深色模式禁止用于大面积实心填充**（主按钮除外，且限 1 个/屏），只允许 ≤10% tint、小图标、1px 描边、文字。

### 5.3 问题三：现有的大面积色块位置

实际代码里已有几处大面积品牌色铺陈，换品牌色后风险会放大：

- `pages/namespace/index.tsx:362` — 整张主卡 `border-primary/20 bg-primary/5 p-5`，是页面上最大的品牌色区域。
- `pages/message/index.tsx:275` — `text-primary/[0.08]` 的 96px 旋转装饰图标。
- `pages/namespace/index.tsx:393` — `size-2` 圆点 + `ring-4 ring-primary/15`，形成发光圈。
- `history-insights.tsx:607` — 柱状图 `bg-primary`，多柱并排时是成片的纯色。
- `--app-gradient` — 顶部 `rgba(22,119,255,0.08)` 径向光晕，固定不随主题变化。

后两项是"发光感"的主要来源。建议：柱状图填充降为 `/85`~`/90` 并去掉 overlay 提亮；顶部光晕从 `0.08` 降到 `0.05`（深色）/`0.06`（浅色），且必须改为 `color-mix(var(--primary))` 以跟随品牌色。

### 5.4 要求 2 与要求 4 的交汇点

深色模式若按 5.1 提亮品牌色（如皇家紫需 +33% 到 `#A16A9A`），提亮后所有色的实心填充都必须改用**深色 on-primary**：

| 品牌色 | 深色实心底 | 白字 | 深字 `#0b1120` | 裁决 |
|---|---|---|---|---|
| 暖阳橙 | `#DB7A0E` | 3.09 | **6.10** | 深字 |
| 矢车菊蓝 | `#5A92E5` | 3.14 | **5.99** | 深字 |
| 翠微 | `#66863E` | 4.16 | **4.52** | 深字 |
| 碧青 | `#41B5C2` | 2.44 | **7.72** | 深字 |
| 柠檬黄 | `#FACA2E` | 1.55 | **12.15** | 深字 |
| 梅洛粉 | `#EB6D98` | 2.93 | **6.43** | 深字 |
| 皇家紫 | `#A16A9A` | 4.16 | **4.52** | 深字 |

**深色模式 7/7 全部必须用深色 on-primary。** 这意味着 `--primary-foreground` 在两个模式下取值相反（浅色白、深色深藏青）——这是必须承认的 token 设计事实，不是可选项。

## 6. 推荐 token 矩阵

| 角色 | token | 用途 |

## 9. PASS 标准

任一未满足即维持 HOLD：

- [ ] **B1 已澄清**：明确是「选一色」还是「7 色可切换」，并据此确定验收范围
- [ ] **品牌色单源化**：全局无 `#1677ff` 硬编码（含 14 个 unDraw 插图），`--app-gradient` / `--chart-1` / `--ring` / `--sidebar-*` 全部联动
- [ ] **三个品牌 token 角色分离**：`--primary`（填充）、`--primary-ink`（文字）、`--primary-ink-muted`（chip），浅深两模式各自取值
- [ ] **on-primary 逐色决定并落地**：浅色模式全部白字达 AA；深色模式全部深色字达 AA
- [ ] **焦点环 ≥ 3:1**，浅深两模式均以像素实测验证
- [ ] **chip 小字 ≥ 4.5**，在 10% tint 实测底上验证，不是在白底上推算

- [ ] **深色模式 Y ≥ 0.45 的品牌色禁止大面积实心填充**
- [ ] **交互态（hover/active/disabled）逐态实测**，不能只验静止态
- [ ] **1440px 与 390px 双视口截图**，覆盖加载/空/错误/禁用/选中状态

- [ ] 浅色模式 7 色中若为「可切换」：**每一色都通过全部 8 项**，不做"平均通过"

## 10. 落地顺序建议

1. **先确认 B1**（范围决策），**再修 B3–B10**（与品牌色无关的既有 a11y 缺陷，可独立合入、独立验证）
2. **token 单源化（B2）**，此时代码才具备换色的能力
3. **引入三角色 token**，用现状 `#1677ff` 先跑通并验证在浅深两模式下全部达标
4. **再逐色接入候选色**，每接入一色跑一次全量清单，不通过的色直接退回调色，不允许"先上线后补"
5. 柠檬黄、碧青若必须保留品牌识别，仅用于**深色模式**与**logo/插画**，浅色模式 UI 采用其压深衍生值——并在设计规范里写明这是同一品牌的深浅两个使用层级，不是两个品牌
