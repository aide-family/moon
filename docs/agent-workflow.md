# Agent 工作方式：效率与准确性

这份文档规定 agent 在本仓库干活时**怎么用工具、怎么控制步数、什么时候验证、什么时候并行**。
它不是风格建议：下面每一条都对应一次真实的耗时统计。诊断证据见 §6。

目标不是"快"，是**用更少的步数拿到更可靠的结论**——步数越多，出错和返工的概率越高。

## 1. 工具路由（硬性）

| 要做的事 | 用什么 | 不要用 |
| --- | --- | --- |
| 读文件 | `read`（多文件用 `ops_read_files`） | `cat`、`sed -n`、`head`、`tail` |
| 找文件 | `glob` | `ls`、`find`、`git ls-files` |
| 搜内容 | `grep` | `grep -r`、`rg`、`ag` 走 bash |
| 跑命令 | `bash` | — |

- **bash 只跑命令**：git、make、npm、go、kubectl、脚本。它不该出现在"我想看看这个文件"的路径上。
- **同一路径在一次会话里只读一次**。需要更多内容用 `offset`/`limit` 续读，不要重读整个文件。
- **批量读**：一次 `ops_read_files` 可以带最多 32 个文件区间，别一个文件一次调用。
- 大文件（>500 行）先 `grep` 定位行号，再按区间读，不要整篇加载。

## 2. 步数预算与批处理

- **单任务预期 ≤80 step**；到 **120 step** 还没收尾，先停下来汇报：已完成什么、剩什么、为什么超出、预计还要多少步。
- **独立操作合并在同一轮**：同一 response 里并发发多个 tool call，不要串行等结果。
  - 例：`git status` + `git branch --show-current` + `ls` 合并成一条；多个文件的 `read` 合并成一次调用。
- **长任务一律后台**：起服务、构建、全量测试、集群等待，用后台 job，再用 `job_output` 取结果。
  **禁止 `sleep 30` 以上的轮询**——那是把 agent 时间换成运气。
- 开工基线只需一条：`git branch --show-current; git rev-parse --short HEAD; git status --porcelain`。

## 3. 验证分级

按**改动范围**选验证，不按"心里没底"选。完整矩阵见 [quality-gate.md](quality-gate.md#31-验证矩阵)。

- 改哪个包就测哪个包：`go test ./internal/data/...`，不要一上来 `make test` 全仓。
- `typecheck` / `lint` 每个任务各跑一次；同一命令在一个任务里**最多跑一次**，除非你又改了它覆盖的范围。
- 全量（`make vet && make lint && make test`、`npm run check && npm run build`）**只在交付前跑一次**。
- 浏览器验收用现成脚本，**不要现场手搓 CDP/Playwright 脚本**：
  `npm --prefix web run check`、`npm --prefix web run smoke`、`npm --prefix web run e2e`。
  缺场景就补到 `web/e2e/` 的用例里，下次直接复用。
- 跑不动就写"未验证"，不要加一轮"我应该再确认一下"的探索。

## 4. 并行与编排门禁

多智能体不是默认选项，是**有并行收益时才用**的工具。

- 先问一句：**一个 agent 能不能做完？** 能，就直接做。
- 只有满足以下全部条件才开 team：≥2 个**互不依赖**的修改范围、每个都有明确验收、合并成本低于收益。
- 开之前把任务卡写死：目标、可改文件、验收命令、禁止事项。含糊的任务卡会在 `wait_agent` 上变成十几分钟的空转。
- `wait_agent` 之前先 `list_agents`；不要轮询 `list_agents`，等唤醒。
- 专家（`summon_expert`）用于**需要领域判断**的环节，不用于"帮我读文件"。

## 5. 上下文卫生

- **按需读文档**：先看 [AGENTS.md](../AGENTS.md) 的文档地图，只打开本任务需要的那几份，读相关章节。
- 不要为了"了解背景"把 `docs/design.md`（681 行）、`docs/roadmap.md`（485 行）整篇读进上下文；
  用 `grep` 定位章节再读。
- 任务结束前清理：不留临时脚本、不把 `tmp/` 产物加进提交。

## 6. 诊断证据（2026-11-06，260 个会话 / 108 个任务）

| 指标 | 数值 | 结论 |
| --- | --- | --- |
| 单任务中位 | 171 step / 231 次工具调用 / 31.2 分钟 | 步数是主要成本 |
| bash 占比 | 67.6%（38,671 次调用里 25,862 次） | 文件检索跑在 bash 里 |
| 检索类 bash | ≈13,000 次，约 28% 有效时长 | `cat/grep/sed/ls` 是可优化的最大单项 |
| 重复读 | 4,000 次 read 中 1,304 次同文件重复（32.6%） | 读一次就够 |
| 编排等待 | 1,779 分钟（17%）；编排任务中位时长 2.5× | 门禁缺失 |
| 验证命令 | 3,871 次 / 843 分钟（10%），单任务重复 5–6 次 | 分级验证缺失 |
| 工具面 | 可用 102 个工具，260 个会话里 50 个从未使用 | 提示词与 schema 冗余 |
| 上下文 | 中位 122.6k tokens，峰值 522.6k，仅 40 次压缩 | 只涨不压 |

修完前四项，按保守估计单任务有效时长可降 30% 以上，且返工率同步下降（少走弯路 = 少出错）。
