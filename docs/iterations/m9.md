# M9 平台用户与邀请确认

通用规范见 [conventions.md](conventions.md)。本步补充 M1 的身份模型，不改变告警、通知和边缘执行。

## 目标与依赖

用户从“租户内的全局身份”改为“独立于租户的平台身份”；租户邀请必须由被邀请人在平台确认；系统权限和租户权限彻底分开。

依赖：M1。

## 需求约束

1. 用户列表独立管理。第一个注册用户是超级管理员，后续用户的平台角色由超级管理员授权。
2. 租户邀请成员必须先生成平台邀请消息；被邀请人点击同意后才成为成员。
3. 邀请邮件携带快捷链接。未注册用户打开链接后引导注册，注册完成自动登录并打开邀请函。
4. 系统权限和租户权限分开。用户列表只能由系统管理员及以上查看。

## 数据

| 实体 | 要点 |
| --- | --- |
| `User` | 增加 `system_role`（`SUPER_ADMIN` / `SYSTEM_ADMIN` / `USER`）和 `authorized_by`。`system_role = 'SUPER_ADMIN'` 使用部分唯一索引，保证只有一个超级管理员 |
| `MemberInvite` | `uid`、`namespace_uid`、`email`、`user_uid`（未注册为空）、`role_uid`、`inviter_uid`、`token_hash`、`status`、`expires_at`、`responded_at`。令牌只存 SHA-256 摘要；`(namespace_uid, email)` 在 `PENDING` 上唯一 |
| `Member` | 新流程只在确认邀请后创建 `JOINED`。不再由管理员直接创建 `INVITED` 成员 |
| `SystemMessage` | `user_uid` 或 `email`、类型（`INVITE_RECEIVED` / `INVITE_ACCEPTED` / `INVITE_DECLINED`）、触发人、租户、角色、`read_at`。邀请收到、接受和拒绝都会写一条 |

已有部署升级时，seed 会把最早注册且没有超级管理员的用户补为 `SUPER_ADMIN`。新库的第一个注册用户由 `CreateUser` 在数据库部分唯一索引保护下确定。

## 系统权限

系统权限不写入租户 `permissions` 表，由 `app/alioth/pkg/perm` 单独维护：

| 权限 | 说明 |
| --- | --- |
| `system:user:read` | 查看平台用户列表和详情 |
| `system:user:write` | 封禁、解封普通用户 |
| `system:role:read` | 查看平台角色 |
| `system:role:write` | 授权或撤销系统管理员，仅超级管理员 |
| `system:invite:read` | 查看平台邀请消息 |

| 平台角色 | 权限 |
| --- | --- |
| `SUPER_ADMIN` | 全部系统权限 |
| `SYSTEM_ADMIN` | `system:user:read`、`system:user:write`、`system:role:read`、`system:invite:read` |
| `USER` | 无 |

`access.RequireSystem` 不读 `X-Namespace`。`UserService` 的列表、详情、封禁、解封和系统角色授权都走它。超级管理员不能封禁或降级自己，也不能操作另一个超级管理员；系统管理员不能操作系统管理员或超级管理员。

## 邀请流程

1. 租户管理员提交邮箱和角色。服务端校验 `member:write`、角色不属于 `owner`，生成 256 位随机令牌并只保存摘要。
2. 已注册邮箱匹配 `user_uid`；未注册邮箱留空，注册后按邮箱匹配。
3. 同一租户同一邮箱重复邀请时刷新令牌、角色和 7 天有效期，不新增消息。
4. 服务端尝试发送邀请邮件。邮件正文包含 `{web_url}/invite/{token}`。邮件失败只记录日志，邀请仍然有效。
5. 被邀请人通过 `GET /v1/self/invitations` 查看平台消息，或打开邮件链接 `GET /v1/invitation/{token}`。
6. 未登录用户被引导到登录/注册。注册页预填邀请邮箱，注册成功后保存会话并回到邀请函。
7. `POST /v1/invitation/accept` 校验当前用户与邀请邮箱或 `user_uid` 一致、邀请未过期、角色仍启用，然后创建 `Member`、写入 `MemberRole`，邀请改为 `ACCEPTED`。
8. `POST /v1/invitation/decline` 只改为 `DECLINED`，不创建成员。租户管理员可通过 `DELETE /v1/member/invite/{uid}` 撤销 `PENDING` 邀请。过期邀请由列表读取时惰性标记为 `EXPIRED`。

## 系统消息

1. 邀请创建时给被邀请人写一条 `INVITE_RECEIVED` 消息。已注册用户写 `user_uid`；未注册邮箱写 `email`，注册后按邮箱匹配。
2. 被邀请人同意时给邀请人写 `INVITE_ACCEPTED`；拒绝时写 `INVITE_DECLINED`。触发人是被邀请人。
3. 同意或拒绝后，把同一邀请的 `INVITE_RECEIVED` 标为已读，避免被邀请人的未读角标残留。
4. 成员被移出租户时，给被移除用户写 `MEMBER_REMOVED`，记录操作人和租户名称。
5. 消息页支持分页、只看未读、单条已读、全部已读；顶栏铃铛显示未读数，每 30 秒刷新一次。
6. 邀请消息上的操作分别跳转到邀请函或成员页；被移出的消息跳转到租户页并刷新会话。

## Web

- 平台用户页：仅 `system:user:read` 可见，展示平台角色；超级管理员可打开“授权平台角色”对话框。
- 成员页：保留成员列表；新增“待确认邀请”表，可撤销邀请。邀请提交后提示“等待对方确认”。
- 邀请收件箱：`/invitations` 对所有登录用户可见，入口放在账户菜单中，和个人资料并列，不占侧栏菜单；可同意或拒绝，同意后切换到邀请所属租户。
- 邀请函落地页：`/invite/:token` 不需要登录。未登录时显示登录/注册入口；注册成功自动登录后回到本页。
- 系统消息页：`/messages`，入口放在账户菜单和顶栏铃铛，不占侧栏。未读消息高亮，支持单条和全部已读。
- 登录和注册支持 `next` 参数，只接受站内绝对路径。

## 验收标准

- [x] 新库第一个注册用户是 `SUPER_ADMIN`，第二个用户是 `USER`。
- [x] `USER` 调用 `GET /v1/users` 返回 403；`SYSTEM_ADMIN` 和 `SUPER_ADMIN` 可以查看平台全部用户。
- [x] 超级管理员把普通用户授权为 `SYSTEM_ADMIN`；该用户获得用户列表权限，但仍不能调用 `system:role:write`。
- [x] 普通用户被邀请后，成员列表在同意前不出现该用户；平台邀请列表出现 `PENDING`。
- [x] 用户同意后出现 `JOINED` 成员并带上邀请角色；拒绝或撤销不创建成员。
- [x] 邀请邮件通过 Mailpit 收到，正文链接可打开公开邀请函；未注册邮箱注册后自动登录并完成确认。
- [x] 非受邀邮箱调用同意接口返回 403；过期邀请不能同意。
- [x] 邀请创建后被邀请人收到 `INVITE_RECEIVED` 系统消息；未注册邮箱注册后能看到该消息。
- [x] 被邀请人同意或拒绝后，邀请人分别收到 `INVITE_ACCEPTED` / `INVITE_DECLINED` 消息；被邀请人的邀请消息自动已读。
- [x] 未读数、单条已读和全部已读接口正确；顶栏铃铛与消息页同步。
- [x] 用户被移出租户后收到 `MEMBER_REMOVED` 消息，随后失去该租户权限。
- [x] 已有部署升级后，最早注册的用户被补为 `SUPER_ADMIN`。

## 口径说明

“后续用户由该用户授权”在本步实现为平台角色授权：第一个注册用户是超级管理员，只有超级管理员可以授予或撤销 `SYSTEM_ADMIN`。注册本身保持开放，因为需求要求未注册的被邀请人能够通过邀请邮件完成注册并自动登录；被邀请人加入租户仍需本人确认。若后续产品要求“注册后必须由超级管理员审批才能登录”，需要新增账号审批状态，并让邀请注册自动带入审批通过标记。
