# M1 身份与租户

通用规范见 [conventions.md](conventions.md)。

## 目标与依赖

浏览器可以注册、登录，并在 Namespace 内按 RBAC 使用管理台。

依赖：M0。

## 范围与不做

做：用户、OAuth 身份、Namespace、成员、角色、权限、注册、三种登录、JWT、封禁、Web 壳。

不做：数据源、规则、通知、Agent。不做探测任务和微前端。成员关系不再使用 Moon 那种单独的 `MemberRole` 枚举作为唯一授权手段；预置角色通过 `Role` 与 `MemberRole` 表生效。

## 开发细则

### 数据

在 `alioth` 的 ent schema 增加：

| 实体 | 要点 |
| --- | --- |
| `User` | UID、名称、昵称、邮箱、头像、备注、状态 `ACTIVE` / `BANNED`、`password_hash` |
| `UserOAuth` | OpenID、来源应用、原始资料。来源为 GitHub、Gitee、飞书 |
| `Namespace` | UID、名称、Secret、状态、负责人、Metadata、Logo、Banners |
| `Member` | 用户与 Namespace。状态 `JOINED` / `INVITED` / `EXPIRED` |
| `Role` | Namespace 内角色，或系统预置角色 |
| `Permission` | `resource:action`。全局，不带 `namespace_uid` |
| `RolePermission` | 角色与权限 |
| `MemberRole` | 成员与角色，一个成员可以有多个角色 |

`User`、`UserOAuth`、`Permission` 是全局表。`Namespace` 自身以 UID 区分租户。`Member`、`Role`、`RolePermission`、`MemberRole` 带租户。名称在同一 Namespace 的未删除记录上唯一。

种子数据写入四档预置角色。权限资源与动作见通用规范。绑定关系：

- `owner` 拥有全部权限，包括删除 Namespace 和移交 owner。
- `admin` 拥有管理权限，不包括删除 Namespace 和移交 owner。
- `member` 拥有配置的读权限、告警处理权限，以及后续里程碑才会用到的 `ssh:exec`、`sftp:read`、`sftp:write`、`k8s:proxy` 中已经授权的部分。本步先把这些权限码种进表，页面可以不出现对应菜单。
- `viewer` 只有各资源的 `read`。

创建 Namespace 的用户成为该空间的 `owner`。

### 认证

能力来自 Moon goddess，并增加注册和密码登录。路径在 `api/alioth/v1` 定稿。行为如下：

- 注册：邮箱、密码、图形验证码。图形验证码对应 Moon 的 `GET /v1/captcha`。密码只写哈希。
- 密码登录：邮箱与密码，成功后签发 JWT。
- 邮箱验证码登录：先发码，再凭邮箱和验证码登录。对应 Moon 的 `POST /v1/auth/email/login/code` 与 `POST /v1/auth/email/login`。
- OAuth2：GitHub、Gitee、飞书。对应 Moon 的 `POST /v1/auth/oauth2/login`。首次登录创建 `User` 与 `UserOAuth`。
- 刷新令牌。对应 Moon 的 `GET /v1/self/refresh-token`。
- 当前用户：资料、所属 Namespace、修改邮箱、头像、备注。对应 Moon 的 `Self`。
- 封禁与解封。对应 Moon 的 `BanUser` / `PermitUser`。被封禁用户的 JWT 不能访问业务接口。

service key 在配置中按调用方预留，形态为 `Authorization: Bearer sk-...`。本步还没有 `megrez` 业务调用。中间件必须让用户 JWT 与 service key 互斥：带 service key 的请求不能进入管理页面所用的用户接口。

业务接口读取 `X-Namespace`。没有该头时返回客户端错误。列表和写入都加上这个租户条件。

### 管理能力

沿用 Moon 的资源行为，由 `alioth` 实现一次：

- Namespace 的创建、更新、启停、删除、列表
- 用户列表、封禁、解封
- 成员列表、邀请、移除、状态变更
- 角色的增删改查与启停，为角色分配权限，为成员分配角色
- 读取当前用户权限，供菜单使用

删除 Namespace 和移交 owner 只允许 `owner`。`admin` 调用这两项得到无权限。

### Web

页面：登录、注册、个人资料、Namespace、用户、成员、角色与权限。

壳：侧栏、顶栏、Namespace 切换、主题、中英文。没有 Namespace 时引导创建。切换 Namespace 后，后续请求使用新的 `X-Namespace`。

菜单根据权限接口的结果生成，不在前端写死四套菜单。`viewer` 看不到写操作入口；即使手工调用接口，服务端也拒绝。

请求从 `web/src/api` 发出，带 Bearer 和 `X-Namespace`。401 时清除令牌并进入登录页。

## 本步规范

- 密码字段只出现哈希。日志不打印密码、验证码和 JWT。
- 授权判断放在 `alioth` 的 biz。`service` 不拼接 SQL，也不只靠前端隐藏按钮。
- 查询条件必须含当前 `namespace_uid`，禁止先查出全表再在内存里过滤租户。
- OAuth 的 client secret 放在环境变量，不写进仓库。

## 验收标准

- [ ] 不带用户 JWT 调用业务接口，返回未认证。
- [ ] 使用 service key 调用个人资料或成员管理接口，被拒绝。
- [ ] 在 `http://<web>:8080` 完成注册和密码登录，打开个人资料并修改备注。
- [ ] 邮箱验证码登录走通。已配置的 GitHub、Gitee 或飞书 OAuth2 至少走通一种；未配置的来源在验收记录里标明跳过原因。
- [ ] 创建 Namespace A 与 B。A 中的成员和角色用 B 的 `X-Namespace` 查询不到。
- [ ] `viewer` 调用任一写接口被拒绝。`admin` 删除 Namespace 和移交 owner 被拒绝。`owner` 可以完成这两项。
- [ ] 切换 Namespace 后，下一次请求的 `X-Namespace` 是新值。没有 Namespace 时页面引导创建。
- [ ] 封禁用户后原令牌不能访问业务接口。解封后可以重新登录。
- [ ] 浏览器里 API 只出现在 8080。数据库中的 `password_hash` 不是明文密码。
