# M3 天权评测

通用规范见 [conventions.md](conventions.md)。

## 目标与依赖

`megrez` 评测已启用的指标规则，写回实时告警和恢复。多个副本不重复评测。

依赖：M2。

## 范围与不做

做：调度、领取、指标评测、事件、人工处理、实时与历史页面。

不做：通知投递。FIRING 可以先记下应当通知的规则，真正的 `NotificationTask` 在 M4 生成；若本步为了表结构提前建任务表，任务必须保持不发送。Logs 与 Trace 规则被调度时只回写「未评测」，不产生 FIRING。不使用进程内 channel 在副本之间传结果。

## 开发细则

### 数据

在 `alioth` 增加 `AlertEvent`，使用 PostgreSQL 声明式时间分区。

事件状态：`FIRING`、`RECOVERED`、`RECOVERED_BY_MANUAL`。

当前 FIRING 在 `(namespace_uid, fingerprint)` 上唯一。评测批次在 `(rule_uid, datasource_uid, eval_slot)` 上唯一。fingerprint 为 `Of(rule_uid, datasource_uid, labels)`：同一规则、同一数据源、同一指标标签组得到同一个 fingerprint。

规则不再绑定单个 `datasource_uid`，而用 **类型 + `datasource_labels` 匹配器** 确定范围。匹配器中的每个 key=value 都必须出现在数据源 `labels` 中，且 `type` 相等、`status=ACTIVE`；空匹配器表示该类型下全部 ACTIVE 数据源。Claim 时对每个匹配数据源各产出一条规则快照并分别评测。

实时列表是状态为 FIRING 且未被抑制的事件。历史列表是已恢复和已抑制的事件。

### 调度

`alioth` 周期扫描 `next_eval_at <= now` 且已启用的规则。扫描包在 `alioth:lock:schedule:eval` 里，TTL 15 秒，不续期。扫描时写下一次评测时间，然后释放锁。

停用规则不进入候选。Logs 与 Trace 可以进入候选，但 `megrez` 看到未实现的驱动时跳过评测。

### megrez

`api/megrez/v1` 由 `alioth` 实现，`megrez` 用自己的 service key 调用：

- 领取到期规则快照，包含表达式、条件、数据源连接所需的解密配置、当前 FIRING fingerprint
- 回写 FIRING、恢复，或未实现驱动

`megrez` 的步骤：

1. 领取快照。
2. 对 `alioth:lock:eval:{rule_uid}:{datasource_uid}` 执行 `SET NX PX`，TTL 30 秒。失败则跳过该（规则, 数据源）对。
3. 每 10 秒续期。指标规则按 Moon 已实现的路径查询：PromQL、`query_range`、比较条件、采样 FOR / MAX / MIN，得到含 datasource 的 fingerprint。
4. 回写。原先 FIRING 而本次未命中，记为恢复。续期失败则不回写成功。
5. 释放锁。错误 token 不能释放别人的锁。

`megrez` 直接查询数据源，不把查询请求绕回浏览器。它不监听除 8001 `/health` 以外的 HTTP，不对外提供 gRPC。

用户 JWT 调用领取和回写被拒绝。

### 人工处理

沿用 Moon 实时告警的行为：介入、批量介入、抑制、恢复、批量恢复、统计。手工恢复的状态是 `RECOVERED_BY_MANUAL`。这些接口要求 `alert:intervene` 或等价的告警写权限。`viewer` 只读。

### Web

实时告警：筛选、详情、介入、抑制、恢复；固定「我的告警」Tab，以及用户订阅的告警页面 Tab。告警页面按标签匹配过滤，支持公开/私有与个人选用。历史告警：筛选和列表。状态与库里的 `AlertEvent` 一致。

## 本步规范

- 持锁进程是 `megrez`。`alioth` 不替 `megrez` 持有 `alioth:lock:eval:*`。
- 回写按 fingerprint 幂等，且带 `datasource_uid`。重复回写不新增第二条当前 FIRING。
- Redis 断开时 `megrez` 停止评测并记录失败。不得在无锁时继续查询并回写。
- 无匹配数据源时该规则本轮不发快照。
- 数据源凭据只在领取快照的内部响应里出现，不写进 `megrez` 的日志。

## 验收标准

- [ ] 创建一条会命中的指标规则。一个评测周期后出现一条 FIRING。相同 fingerprint 的再次评测不新增第二条当前 FIRING。
- [ ] 两个同类型、同标签的 ACTIVE 数据源绑定同一规则匹配器后，一个周期内产生两条 FIRING（fingerprint 不同）。改数据源标签使匹配器只命中其一后，下一轮只对命中源评测。
- [ ] 让条件不再命中。该事件变为恢复，恢复记录只有一条。
- [ ] 同时运行两个 `megrez`。同一 `rule_uid` 只有一个副本回写成功，另一个因为没有拿到锁而跳过。
- [ ] 评测过程中停止 Redis。持锁副本续期失败后，这次评测没有被报成成功。恢复 Redis 后下一轮可以继续。
- [ ] 保存一条 Logs 或 Trace 规则并等到调度。回写标明未评测，没有对应 FIRING。
- [ ] 在 `http://<web>:8080` 的实时告警页对一条 FIRING 执行抑制、介入和手工恢复。历史列表与状态一致。`viewer` 的写操作被拒绝。
- [ ] 创建私有告警页面：仅创建者可选入实时 Tab；设为公开后同租户他人可选显示，列表按标签过滤正确。
- [ ] 「我的告警」始终在实时页；仅当用户邮箱（或 UID）在规则绑定通知组 `receivers` 中时出现对应 FIRING。
- [ ] 无 `alert:write` 不能创建/改告警页面；有 `alert:read` 可订阅可选页面。
- [ ] 用用户 JWT 调用领取和回写被拒绝。`megrez` 的 8001 仍然只有 `/health`。
- [ ] 两个 Namespace 的事件互不可见。
